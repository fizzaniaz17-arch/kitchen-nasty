# Generator design and rubric review

> **Header coverage follow-up, 28 November 2026:** The original generated set contained 296 cases. The scoped generator now adds nine optional `Idempotency-Key` header cases, giving 305 cases: omitted, ordinary valid, disallowed pattern, and the 0/1/2 and 127/128/129 length boundary triplets. The PostgreSQL suite sends each generated case through HTTP and checks reservation and idempotency-record persistence; a present empty value is tested separately from omission. The generated-ID audit checks each case exactly once. The generator uses schema minLength, maxLength and pattern; it requires a suitable ASCII sample and does not claim support for every possible future header schema. The older counts, failures and candidate descriptions below are historical.

`tests/team/member-2/reservations.openapi.json` describes the selected route inputs and response structures. The spec labels the documented availability time separately from current handler behavior. UTC-day metadata, whole-object examples and wire-encoded path samples drive the corresponding HTTP tests. Cross-record rules are documented separately; `x-business-scenarios` adds explicit calendar and clock examples without pretending the server's Zod regex enforces them. `x-clamp-boundaries` records pagination thresholds and `x-business-boundaries` records reservation size boundaries for the permissive availability parser. These extensions are test metadata, not claims that the API rejects every value beyond a boundary.

`generate-ep-bva.mjs` reads the JSON spec. For each body property it emits required/omitted, null, type, enum and numeric/string limit cases; it derives path cases and query cases from route parameters and the named extensions. Test IDs include method, path, input and partition. The Vitest suite loads the generated JSON, supplies synthetic related IDs, changes one field per generated case, invokes the Express API, verifies the response and/or database state, and checks documented response shapes with AJV. Separate tests exercise multi-record conditions and auth. `audit-generated-coverage.mjs` compares exact generated IDs with the Vitest JSON report, so an omitted generated case cannot be mistaken for execution. It does not establish that the original spec or set of partitions is complete.

`demo-constraints.mjs` creates a disposable spec file, generates baseline cases with the CLI, changes the reservation maximum 50 -> 40 and table minimum 1 -> 2, runs the CLI again, restores the temporary spec and regenerates. It checks the restored output and SHA-256 match and saves actual before/after triplets in a new evidence file. The checked-in spec and production constraints never change. See [the final regeneration evidence](evidence/audit-final-constraints.json).
