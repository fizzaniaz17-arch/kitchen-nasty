## Persistence and concurrency details for review

`reservation_create_requests` is an additive table with generated ID, authenticated customer ID, key hash, normalized validated payload hash, nullable JSON response, creation timestamp and expiry. A unique `(customerId,keyHash)` index scopes the key to this operation. The row, booking and encrypted response snapshot are written in one transaction. Transaction-scoped PostgreSQL advisory locking serializes the same customer/key, including an absent row; the unique index provides an additional constraint. Other existing reservations are not migrated or changed. Raw keys are not stored. A successful replay uses the original HTTP 201 payload and does not emit another creation event. Records expire after 24 hours and bounded cleanup is implemented; the production schedule is not deployed. Snapshots use authenticated encryption, and the customer foreign key cascades after successful customer deletion. Production key management, backup retention, key abuse limits and disaster recovery require review. No key is required for existing clients.

For conflicts, an interactive Read Committed transaction locks the reservation then affected table rows in sorted order, checks the proposed occupying set and exact slot, and writes only after checking. Cooperating writers are serialized; direct DB writes and future noncooperating paths can bypass the application protocol. Existing duplicates need a separate remediation decision. Do not add a uniqueness constraint without reconciling status semantics and old data.
