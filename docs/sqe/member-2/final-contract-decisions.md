## Persistence and concurrency details for review

`reservation_create_requests` is an additive table with generated ID, authenticated customer ID, key hash, normalized validated payload hash, nullable JSON response and creation timestamp. A unique `(customerId,keyHash)` index scopes the key to this operation. The row, booking and response snapshot are written in one transaction; a uniqueness race rolls back the loser and then replays or rejects based on payload hash. Other existing reservations are not migrated or changed. Raw keys are not stored. A successful replay uses the original HTTP 201 payload and does not emit another creation event. Records currently have no automatic expiry and are not tied by foreign key to the booking; retention, deletion/GDPR policy, ownership lifecycle, key abuse limits and disaster recovery require review before merge. No key is required for existing clients.

For conflicts, an interactive Read Committed transaction locks the reservation then affected table rows in sorted order, checks the proposed occupying set and exact slot, and writes only after checking. Cooperating writers are serialized; direct DB writes and future noncooperating paths can bypass the application protocol. Existing duplicates need a separate remediation decision. Do not add a uniqueness constraint without reconciling status semantics and old data.

Do not close issues or merge until actual required checks, security review, teammate review and branch protection conditions are satisfied. See the defect register and historical evidence for observations before these candidate changes.
