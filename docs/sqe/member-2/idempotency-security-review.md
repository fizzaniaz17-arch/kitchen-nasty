# Idempotency persistence: security review

## Conditional approval and implementation status — 27 November 2026

The user reports that Member 1, Fizza Fatima (`fizzaniaz17-arch`), personally gave conditional approval for 24-hour retention, exact replay, 409 on mismatched payloads, concurrent expiry/reuse, bounded cleanup, secure storage, deletion safeguards and stale-customer JWT rejection. This is not a claimed GitHub approval or Member 3 approval. Deployment remains conditional on encryption-key provisioning, plaintext-snapshot handling, scheduler setup, backup policy and team review.

The implementation uses the database clock, an additive expiry migration and transaction-scoped PostgreSQL advisory locks for absent or existing customer/key pairs. Expired keys can create a new booking, so a retry after the 24-hour window is not protected from duplicates. Cleanup locks expired rows with `SKIP LOCKED` and does not delete a row locked by a live replay. New snapshots are AES-256-GCM encrypted with customer/key/payload binding. Existing unexpired plaintext snapshots are replayed unchanged and encrypted on access; the migration utility below can encrypt them in advance. Expired plaintext is removed by cleanup. Preserve prior migrations and inventory orphans before applying the existing customer foreign key; never silently delete orphan records.

### Operational setup — required before release

Provision a cryptographically random 32-byte key from an external secret manager. Set `IDEMPOTENCY_ACTIVE_KEY_ID` to its nonsecret identifier and `IDEMPOTENCY_ENCRYPTION_KEYS` to a JSON object mapping identifiers to base64 keys. Do not commit or log either secret material or connection credentials. All server instances processing the same database require the same active key and read keyring. For rotation, deploy both old and new keys to every instance, switch the active identifier, and retain each old key until its snapshots have expired, cleanup has completed and backup/restore requirements have been satisfied; removing an old key earlier makes replay fail closed. No automatic rotation or secret-manager integration is provided.

**Coordinated cutover required:** the earlier application version cannot decrypt the new envelopes and does not populate the new required `expiresAt` column. Do not run old and new application versions concurrently against the migrated database. Drain old writers, back up and verify the migration and externally managed keyring, deploy the new version to all writers, run the plaintext migration utility, and validate replay before reopening traffic. This sequence and rollback/restore procedure require deployment-owner review; rolling and rollback compatibility have not been established.

After deploying the additive migration and with externally supplied database and encryption secrets, run the built command `node packages/server/dist/scripts/encrypt-legacy-idempotency.js` repeatedly, monitoring its non-sensitive count, until it reports zero. It handles at most 1,000 unexpired plaintext rows per invocation in batches of 50; row locks and `SKIP LOCKED` avoid competing with live replays. Verify inventory with `SELECT count(*) FROM reservation_create_requests WHERE NOT "responseEncrypted" AND response IS NOT NULL AND "expiresAt" > clock_timestamp();`. Restrict this operation and verify the zero count before enforcing an encrypted-only operating policy. If the command fails, keep the data and investigate; do not remove plaintext or keys to make the check pass.

Schedule `node packages/server/dist/scripts/cleanup-reservation-idempotency.js` at an agreed interval, for example every five minutes through the deployment platform's scheduler. Each invocation removes at most 20 batches of 500 and returns a nonzero exit on error. Alert on failure, elapsed runtime and a growing expired-row backlog; repeat invocations until it drains. **A schedule and monitoring are not deployed by this repository change.** The cleanup role requires schema usage plus only the table SELECT/DELETE and row-lock privileges needed by PostgreSQL; it does not need encryption keys. The legacy-encryption role additionally needs UPDATE on the snapshot and encryption-marker columns and access to the externally managed keyring. Validate exact grants and row-level security in the deployment environment.

The customer foreign key cascades snapshots only after a successful customer deletion. Existing reservation and other dependencies may block that deletion; this is not full account erasure. Authentication now checks customer existence, including on optional-auth routes when a customer token is supplied. This does not revoke other active tokens for a still-existing account, implement `tokenVersion`, or prevent an old token from becoming usable if an account is recreated with the same customer ID. Database backups may retain old plaintext and deleted data until separately managed backup expiry; agree retention, access, restore and erasure policy before release.

Before applying the earlier customer-cascade migration to an existing database, inventory orphaned records without exposing snapshot contents: `SELECT count(*) FROM reservation_create_requests r LEFT JOIN customers c ON c.id = r."customerId" WHERE c.id IS NULL;`. If the count is nonzero, stop deployment, preserve a restricted backup and have an authorized owner decide a case-by-case remediation; do not run an automatic delete. The expiry migration treats the prior timezone-less `createdAt` values as UTC when backfilling. Verify the historical database/session timezone and data provenance before deployment; if UTC cannot be established, stop and approve a data-specific backfill rather than silently assuming the 24-hour cutoff is accurate.

## Earlier analysis and proposed design

The following sections preserve the earlier pre-approval analysis. Statements below that describe expiry or encryption as unimplemented are historical; see the current implementation and deployment status above.

The reservation retry contract is optional and customer-scoped. A unique `(customerId, keyHash)` and a single database transaction protect cooperating concurrent requests; a matching payload replays the original 201 response, a different valid payload returns 409, and requests without keys remain separate. The raw key is not persisted. Hashes are not encryption and low-entropy keys or payloads can be guessed offline by someone with database access. A keyed HMAC would require an independently managed, rotatable server key and a migration plan.

The stored JSON response duplicates the reservation result, including customer name and email. This supports exact replay even after the original reservation changes, but duplicates personal information and potentially becomes stale. Database credentials and backups must be restricted as personal data; logs redact authorization, cookies and idempotency keys. The current implementation has no expiry, background cleanup or encryption specific to snapshots. Authentication checks the signed customer identity, and lookup is scoped to that customer; the authentication middleware does not itself check whether the customer still exists in the database.

The follow-up migration adds a customer foreign key with `ON DELETE CASCADE` so a *successful customer deletion* also removes replay snapshots. Existing reservation and other foreign keys may prevent customer deletion until separately handled; this change does not define or implement a full account-erasure workflow. Existing orphan snapshot rows would cause the migration to fail instead of being silently deleted; inventory and an authorized remediation plan are required before deploying in an environment where the earlier migration was already used.

## Recommendation for team decision before merge

Approve an explicit, published idempotency window based on actual client retry behavior, with a **proposed 24-hour window** as a review starting point, not an implemented or approved duration. Decide whether the exact original response must be replayed for the whole window or whether a minimal booking identifier and current authorized representation are acceptable. If exact replay is required, encrypt restricted snapshots and define key rotation, backup retention and access auditing. On expiry, clean rows through a scheduled and monitored job; document that reusing a key after expiry can create a new reservation. Apply deletion or anonymization to active rows and backups according to the team's approved account-erasure and legal policy. Specify handling for concurrent requests during expiry and for already orphaned rows. Confirm client requirements before implementing expiration or changing replay behavior.

No retention period or backup policy is silently enacted by this review. Until the team accepts a policy and its implementation, do not merge the idempotency storage design. Separately review the current signed-token lifecycle and deletion behavior; the new foreign key does not revoke already issued JWTs.

## Proposed implementation patch — not applied, pending approval

1. Add `expiresAt` and an index using a **new** additive migration. Backfill existing rows only after the team selects the retention start and treatment of old or orphaned snapshots. Do not edit the two existing migrations or silently delete orphans.
2. For a new keyed request, set expiry to transaction creation time plus the approved window. Until expiry, retain the originally approved exact-201 replay contract. The response currently contains customer fields: review whether a future version may return a minimal receipt instead, because reconstructing a response from a changed booking would no longer replay the original response. Encrypt any retained response snapshot with an application-managed key, restricting key access, documenting rotation and ensuring sensitive data is not logged.
3. Serialize lookup/replay, expiration and cleanup through a row-level lock on `(customerId,keyHash)` in one transaction. Define a single database-clock cutoff and unique-index conflict retry for a cleanup/request race. A record locked for an in-flight replay cannot be removed by the cleanup transaction. Explicitly approve the post-expiry behavior: deletion and key reuse can create a new booking, while retaining only a tombstone can reject reuse without retaining the response. A 24-hour tombstone is not automatically sufficient for either product or legal requirements.
4. Run an idempotent scheduled cleanup with bounded batches, retry, monitoring and an independently reviewed service account. Limit database read access to the application and authorized operators. Agree backup expiry and deletion/anonymization procedures; deleting a live row does not erase historical backups.
5. On customer deletion, remove associated snapshots using the existing cascade after required reservation dependencies are handled. Inventory orphans before migration and obtain an approved reconciliation plan. Add customer existence or token-version checks, plus explicit token revocation, as part of the team-approved account-deletion design; the current JWT remains valid until expiry.
6. Test just-before/at/after expiry, replay versus cleanup contention, key reuse, crashes, encryption/key rotation, account deletion, orphaned upgrades and backup procedures in disposable environments. Document that no existing data or prior migration checksum is altered without an approved migration.

The team must approve the window, exact-response versus minimal-receipt contract, expiry/reuse semantics, encryption and key ownership, deletion and backup periods, and token revocation together. This is a design proposal, not runnable or deployed code.
